# ADR-001: Технологический стек WTF

## Статус

Принято.

## Контекст

WTF должен быть self-hosted first, расширяемым и удобным для разработки в открытом монорепозитории. Референс Huly показывает ценность пакетных границ, событийной модели и отдельного слоя совместной работы, но его полный сервисный масштаб избыточен для первого устойчивого ядра WTF.

## Решение

Мы используем:

- `pnpm workspaces` + Turborepo для монорепозитория.
- TypeScript strict mode во всех пакетах.
- React + Next.js для web-приложения.
- TailwindCSS для прикладной стилизации и `@wtf/ui` для переиспользуемых компонентов.
- Zustand для легкого клиентского состояния.
- Fastify вместо Express для API.
- REST для CRUD-контрактов и WebSocket для real-time событий.
- Yjs как CRDT-ядро совместного редактирования.
- PostgreSQL как основное хранилище.
- Redis для pub/sub и кэша real-time слоя.
- Drizzle ORM для типизированной схемы и миграций.
- JWT access tokens + refresh tokens; OAuth2 провайдеры Google и GitHub через переменные окружения.
- S3-совместимое хранилище, локально MinIO.
- Docker Compose для локального self-hosted запуска; структура образов совместима с Kubernetes.

## Почему Fastify, а не Express

Fastify дает встроенную структурированную логгируемость через Pino, строгую plugin-модель, высокую производительность и зрелую интеграцию OpenAPI. Express остается гибким, но требует больше ручной дисциплины для схем, логирования, lifecycle hooks и типизированной композиции.

## Почему Turborepo, а не Nx

Nx сильнее в крупных enterprise-репозиториях с генераторами и policy-driven workflow. Для первого этапа WTF важнее простая модель workspace-пакетов, быстрый кеш и низкая стоимость входа. Turborepo покрывает эти требования без лишнего управляющего слоя.

## Почему Yjs

Совместное редактирование rich text и документов требует устойчивости к offline/online конфликтам. CRDT через Yjs проще эксплуатировать для self-hosted инсталляций, чем централизованные operational transforms, где сервер должен быть единственным арбитром порядка операций.

## Последствия

Пакет `@wtf/core` не имеет runtime-зависимостей и остается переносимым. Infrastructure-детали изолированы в адаптерах. При росте нагрузки API, realtime и worker-процессы можно разделить на отдельные сервисы без изменения доменных агрегатов.
